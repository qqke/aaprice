# 楽天联盟 MVP 上线流程

## 首批 50 个商品

1. 打开管理后台“业务”页的“商业商品候选”；系统已按真实浏览、查价、收藏和近期价格自动排出 50 件。
2. 点击“复制候选清单”，将 `product_id`、JAN 与商品名 TSV 粘贴到工作表。
3. 在楽天商品搜索中用 JAN 核对产品并生成对应 affiliate URL；跳过无对应商品或信息不一致的候选。当前首批 50 件已于 2026-09-01 完成精确匹配、追踪跳转验证并启用。
4. 将工作表整理为每行 `product_id + Tab + HTTPS affiliate URL`，粘贴到“批量导入商业链接”。
5. 首次导入不要勾选“立即启用”。逐条打开目标 URL，核对商品、HTTPS 域名和联盟参数后再启用。

同一商品首期只启用一个合作链接，避免入口竞争和归因歧义。

后续批次可用仓库内工具生成待审核数据。`--validate` 会要求楽天存在包含同一 JAN 的商品页，并确认联盟链接返回官方追踪跳转；`--sql` 只会在全部校验通过时输出事务 SQL：

```bash
node scripts/generate-rakuten-offers.mjs --validate JAN1 JAN2
node scripts/generate-rakuten-offers.mjs --validate --sql JAN1 JAN2
```

执行 SQL 前仍需人工抽查商品规格与数量，避免 JAN 相同但页面销售组合不同。

## 每周检查

- 在 AAPRICE 后台记录商业出口会话、点击数和查价后行动率。
- 商业出口点击率以“归因点击会话 ÷ 有效曝光会话”评估，初始目标 ≥ 8%。有效曝光要求购买按钮至少一半进入可见标签页的视口；归因点击必须匹配同一会话、入口来源与合作链接，发生在该曝光之后，且两者均在所选时间窗内。每个会话在总计中仅算一次。
- 仅使用 `viewport_v1` 埋点；旧版数据加载事件保留在原始日志中，不参与这项比率。无曝光样本显示 —，不能宣称达到或未达到转化目标。浏览器拦截或网络失败可能造成漏记，测试访问也需与真实流量区分。
- 确认合作入口没有降低查价后行动率，也不覆盖门店价格与最低价判断。
- 停用商品不符、失效或跳转异常的链接。
- 从楽天成果报表下载 CSV，人工记录销售额、未确认/确认成果与报酬。

## 当前生产基线

- 2026-09-01：50 个 JAN 精确匹配的合作链接已启用。
- 2026-10-24：修正了加载即算曝光与跨会话点击归因问题，重新开始可见曝光口径；历史 QA 事件不作为新口径的商业验收结果。
- 成交和佣金仍需楽天官方报表证据，覆盖数量与页面点击不等于商业收益。

楽天官方目前说明成果通过网页报表查看，并支持桌面端 CSV 下载；报表通常在 12 小时内反映。未发现公开实时成交 webhook，因此 MVP 不建设伪回调服务。[楽天成果报表说明](https://affiliate.rakuten.co.jp/guides/report/)

## 扩展条件

只有出现以下任一条件时才建设自动成交导入：

- 合作方提供正式 webhook 或服务端成果 API；
- 人工 CSV 对账每周超过 30 分钟；
- 已获得稳定成交，且订单级归因会影响商业决策。
